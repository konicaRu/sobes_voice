# project-starter — общий старт для новых проектов

**Запуск:** в новом проекте скажи — «**Начнём с project-starter**» (или «развернём по
project-starter»). Я читаю файл, провожу стартовый опрос (раздел 2) и разворачиваю проект.

**Три копии — держать синхронными:** `~/.claude/project-starter.md` (главная),
`C:\claude_code_projects\project-starter\project-starter.md` (папка-хаб со всем, что
касается старта проектов — чтобы не искать) и `<корень проекта>/project-starter.md`
(бэкап в проекте). Любую правку правил вношу сразу во ВСЕ три копии.

> Переносимый шаблон правил, общих для всех моих проектов. Когда пользователь говорит
> «начнём с этого файла» (или «развернём по project-starter») — прочитай его целиком,
> пройди **стартовый чек-лист** (раздел 2) по пунктам, затем разверни проект: заведи
> контекстные файлы (раздел 7), при необходимости подключи опциональные модули (8–11) и
> дальше работай по принципам ниже. Файл агент-facing: это инструкция для меня, агента.

## 1. Как использовать

1. Прочитать этот файл.
2. Сначала выяснить цель проекта и стек (пункты 1–2 чек-листа) — без этого не с чем
   сравнивать остальные пункты. Дальше пройти чек-лист (раздел 2) **по пунктам**: по
   каждому коротко сказать, что это, и **объяснить конкретно для этого проекта** — почему
   пункт пригодится или не пригодится (например: «Superpowers — да, тут будет код и
   сабагенты» / «Humanizer — вряд ли, на выходе не текст, а API»), не просто зачитать
   общее описание и дефолт. Спросить «применяем? да/нет», дождаться ответа, не угадывать.
3. По ответам: создать `MEMORY.md`, `ARCHITECTURE.md`, `README.md`; при необходимости
   `git init`; подключить выбранные модули (включая установку скиллов, разделы 10–11).
4. Записать в `MEMORY.md`/`README.md` цель и критерий готовности из ответов.
5. Дальше вести проект по принципам 3–7 + подключённым модулям.

## 2. Стартовый чек-лист установки (идти по пунктам, по каждому спросить «да/нет»)

Это и есть памятка: не вспоминать каждый раз, а пройти список. По каждому пункту —
не просто зачитать описание и дефолт, а **привязать к конкретному проекту**: почему это
пригодится или не пригодится именно здесь, учитывая уже названные цель/стек/масштаб.
Дефолт — отправная точка для решения, а не готовый ответ вместо объяснения. Решает
пользователь, но с пониманием, за счёт чего.

1. **Цель проекта + критерий готовности** — спросить всегда (не пункт да/нет).
2. **Язык** общения и документов — спросить всегда.
3. **Контекстные файлы** `MEMORY.md` / `ARCHITECTURE.md` / `README.md` (раздел 7).
   Дефолт: **да**.
4. **Git** (раздел 6): вести историю? remote (GitHub/GitLab/локально)? пушим? Дефолт: **да**.
5. **Скиллы Карпатого** (раздел 10) — принципы «думай до действия / минимализм / точечные
   изменения / работа от критерия». Дефолт: **да**.
6. **Superpowers** (раздел 11) — скиллы-процессы (brainstorming, TDD, systematic-debugging,
   verification и др.). Дефолт: **спросить** (на проекте с кодом обычно полезно).
7. **Модуль «накопительные правила»** (раздел 8) — для итеративных правил/замечаний.
   Дефолт: **нет**.
8. **Humanizer** (раздел 9) — для проектов, где на выходе текст. Дефолт: **нет**.
9. **Конституция проекта** (раздел 12, по мотивам spec-kit) — короткий свод незыблемых
   принципов (безопасность, данные, процесс, дизайн), на который сверяются спеки/планы/ревью
   и который прокидывается сабагентам-исполнителям/ревьюерам, чтобы не было дрейфа. Дефолт:
   **спросить** (полезно на проектах с кодом и сабагентами; для мелких разовых — избыточно).
10. **Меньше permission-prompts** (раздел 13) — встроенный скилл `fewer-permission-prompts`
    сканирует транскрипты, собирает частые read-only команды и заводит `.claude/settings.json`
    с allowlist. Дефолт: **спросить**.
11. **Плагины claude-plugins-official под стек проекта** (раздел 14) — глянуть официальный
    маркетплейс `github.com/anthropics/claude-plugins-official` и подобрать 2–3 плагина под
    конкретный стек (языковой LSP, интеграция с внешним сервисом, security-ревью и т.п.).
    Дефолт: **да** (просто посмотреть и предложить; ставить — по решению пользователя).
12. **Оформление README** (раздел 15) — традиционный (кратко, без визуала) или «нарядный»
    (badges, оглавление, ASCII-схемы, таблицы, подробные объяснения для новичка) стиль.
    Дефолт: **спросить**.
13. **Карта архитектуры для агента** (раздел 16) — `architecture-map.html` (визуально, для
    человека) + `architecture-map.json` (машиночитаемо, вкладывать в промпт свежему сабагенту).
    Дефолт: **спросить** (полезно, когда проект уже дорос до нескольких подсистем/сабагентов;
    для совсем маленького — избыточно).
    Предлагай модули сам, чтобы пользователь не забыл; решает — он.
14. ub-mode https://github.com/unclebob/ub-mode — небольшой Agent Skill от Robert C. Martin (Uncle Bob), задающий правила качественной разработки для Claude Code, Codex и других coding-агентов.
Заставляет агента работать по принципу Make it Work → Make it Right: минимальная реализация, TDD, проверка результата, исправление первопричины и рефакторинг.
Поддерживает разработку небольшими проверяемыми шагами и помогает не усложнять архитектуру без необходимости.
Дополнительно предлагает quality gates для сложности кода, дублирования и mutation testing через Crapper, Dryer и Mutator.
Можно использовать как инженерный режим Claude Code при разработке production-кода проекта, особенно когда проект становится большим и изменения затрагивают несколько модулей.
При анализе проекта стоит проверить, даст ли ub-mode пользу поверх уже существующих AGENTS.md / CLAUDE.md / Skills и CI-тестов, чтобы не дублировать правила.

## 3. Принципы работы (по Карпатому)

Это текстовый аналог **модуля «Скиллы Карпатого»** (раздел 10): на Claude Code ставится
плагином, на других агентах применяй эти 4 принципа отсюда текстом.

1. **Думай до действия.** При неоднозначности назови варианты и спроси, не выбирай молча.
   Замеченные противоречия выводи, а не сглаживай.
2. **Минимализм.** Делай ровно то, что решает задачу, без запасной «гибкости» и лишнего.
3. **Точечные изменения.** Меняй только нужное; каждое изменение прослеживается к команде.
4. **Работа от критерия.** У задачи есть критерий готовности — гоняй цикл, пока не выполнен.

## 4. Точечные правки — без каскада

Правка по конкретному месту — это точечное изменение, оно не должно «ломать всё»:

- Правь **хирургически** (`Edit` нужного фрагмента), не перезаписывай файл целиком ради
  одной правки, не трогай соседние/несвязанные части.
- Чини указанное + такой же огрех в **текущем** артефакте; уже готовое/отданное задним
  числом не переписывай.
- Не затирай ручные правки пользователя.
- **Не обобщай молча**: после правки спроси — разовая правка или общее правило? Правило
  фиксируй только по подтверждению («запиши / сделай правилом»).

## 5. Стиль работы / экономия токенов

- Отвечай кратко и по делу; без воды и пересказа того, что уже ясно.
- Внутренние рассуждения показывай **процентом готовности** («готовность 60%»), а не
  длинным нарративом.
- Не перечитывай файлы без нужды; не повторяй уже сделанную работу.
- Где есть индекс кода (codegraph/аналог) — используй его вместо grep для структурных
  вопросов; grep — для литерального текста.
- Независимые операции — параллельно (несколько вызовов в одном шаге).

## 6. Git-воркфлоу

- **`git save`** (в конце блока работы): (1) обновить контекстные файлы — дописать запись в
  `MEMORY.md` (сверху) и changelog в `ARCHITECTURE.md`, обновить «Статус»/«Открытые вопросы»;
  прошлое не переписывать, только добавлять; (2) `git add -A`, коммит; если есть remote —
  `git push`. Перед коммитом — sanity-check, что не утекли секреты/приватные данные
  (исключать через `.gitignore`).
  - **ОБЯЗАТЕЛЬНО оба файла, не один.** `MEMORY.md` и changelog `ARCHITECTURE.md` — это разные
    вещи (журнал сессий vs текущая карта проекта), обновление одного не заменяет другое. Нельзя
    пропускать `ARCHITECTURE.md` с мыслью «уже записано в MEMORY, будет дублирование» — именно
    так и было на F1 Predict: `MEMORY.md` вёлся исправно, а `ARCHITECTURE.md` не трогали несколько
    недель, и разделы «Структура/Стек/Команды» (которые описывают ТЕКУЩЕЕ состояние, а не
    историю) протухли и перестали отражать реальность, хотя changelog формально существовал.
    Если `ARCHITECTURE.md` не обновлялся 2+ `git save` подряд — на следующем `git save` сверить
    разделы «Структура/Стек/Roadmap/Команды» с фактическим состоянием проекта и поправить, не
    только дописать changelog-строку.
  - **Если подключён модуль «карта архитектуры»** (раздел 16) — НЕ обновлять
    `architecture-map.html`/`.json` автоматически на каждом `git save` (дорого по токенам,
    большая часть save'ов не меняет архитектуру). Вместо этого на `git save`, где менялась
    структура/схема/автоматика (то же событие, что триггерит правку `ARCHITECTURE.md` выше),
    коротко спросить пользователя: «структура заметно изменилась — обновить карту?» — и делать
    только по ответу «да».
- **`git load`** (в начале сессии): прочитать `MEMORY.md` + ключевые файлы и кратко доложить,
  где остановились. Только чтение.
- **История = откат.** Каждый `git save` — точка отката. Безопасно — `git revert`; один файл —
  `git checkout <commit> -- путь`; `git reset --hard` — только по явной команде пользователя.
- **Многострочный коммит** или сообщение со спецсимволами (`>`, кавычки, скобки) на Windows
  PowerShell писать через файл: `git commit -F .commitmsg.tmp`, затем удалить файл. Иначе
  here-string ломается и слова уходят в pathspec.

## 7. Контекстные файлы (заводить при старте, вести постоянно)

- **`MEMORY.md`** — журнал: «Статус проекта», «Открытые вопросы», «Лог сессий» (свежее сверху).
  Где остановились и почему. Обновляется по `git save`.
- **`ARCHITECTURE.md`** — карта проекта (структура, ключевые файлы, команды) + changelog
  (что и когда меняли). Правила работы не дублировать — только устройство и история.
- **`README.md`** — как пользоваться проектом: назначение, быстрый старт, команды; чтобы
  другой человек/агент мог войти.
  Мини-шаблоны:
  
  ```
  # MEMORY — журнал
  ## Статус проекта
  ## Открытые вопросы
  ## Лог сессий
  ### YYYY-MM-DD (тема)
  ```
  
  ```
  # ARCHITECTURE
  ## Назначение
  ## Структура
  ## Команды
  ## Changelog
  ```

another — `MEMORY.md` is a chronological journal, `ARCHITECTURE.md` is a living snapshot (current

state + changelog), `README.md` is user/contributor-facing documentation (schema, workflows,

commands). On every `git save`:

2. Append a changelog entry to `ARCHITECTURE.md`, AND sync its "current state" sections (structure,

3. **Update `README.md`** wherever the change affects something it documents — schema/table

   descriptions, RLS table, Telegram-notification modes/schedule, structure tree, setup steps, etc.

   Not every change needs a README touch (e.g. an internal refactor with no user-facing or

   documented-behavior change), but default to checking, not skipping.

If any of these three wasn't touched for 2+ consecutive `git save` cycles despite real changes

happening, treat that as a signal to do a full sync pass on its "current state" sections, not just

## 8. Опциональный модуль: накопительные правила

Для проектов, где правила копятся из замечаний (промпты, стайлгайды, политики):

- Замечание/правка → одно **атомарное правило** + скоуп (`always` или условие).
- Перед добавлением — **проверка на противоречия** с базовыми («ядро») правилами и активными.
  Конфликт не разрешать молча — показать и спросить.
- Журнал правил **append-only**: ничего не удалять; отменённое помечать статусом
  (`superseded`/`merged-into-core`); применять только активные.
- Базовый слой («ядро») менять только по явной команде; перенос правила в ядро — отдельным
  действием со сменой статуса.

## 9. Опциональный модуль: humanizer

Для проектов с текстом на выход (письма, посты, доки):

- Финальная шлифовка стиля: живой ритм, человеческий голос, без ИИ-штампов (пафос,
  негативные параллелизмы «не только…, но и», тройки ради ритма, синонимическая жвачка,
  канцелярит, длинные тире, дежурные концовки, филлеры).
- **Не меняет факты, структуру и обязательные требования** — только стиль.
- Состояние держать флагом (напр. строка `on`/`off` в файле). Включать по ответу в опросе.
- Если в среде есть скилл-хуманайзер — использовать его; иначе применять принципы текстом.
- **Источник скилла** (Claude Code) — по языку текста проекта:
  - **Русский** (по умолчанию для моих проектов): `github.com/ilyautov/humanizer-ru`
    
    ```
    git clone https://github.com/ilyautov/humanizer-ru.git ~/.claude/skills/humanizer-ru
    ```
  - **Английский**: `github.com/blader/humanizer`
    
    ```
    git clone https://github.com/blader/humanizer.git ~/.claude/skills/humanizer
    ```
    
    Это не маркетплейс-плагины, а скиллы — ставятся клонированием в локальную папку скиллов.
    Команду выполняет пользователь — подсказать, не вызывать самому.

## 10. Опциональный модуль: скиллы Карпатого

Дисциплина кодинга по 4 принципам из раздела 3 (думай до действия / минимализм / точечные
изменения / работа от критерия). Включать по ответу в чек-листе (дефолт: да).

- **Claude Code** — поставить плагином (источник: `github.com/multica-ai/andrej-karpathy-skills`):
  
  ```
  /plugin marketplace add forrestchang/andrej-karpathy-skills
  /plugin install andrej-karpathy-skills@karpathy-skills
  ```
  
  Команды `/plugin` выполняет пользователь — подсказать их, не пытаться вызвать самому.
- **Claude Code без `/plugin`** (напр. VSCode-расширение — команда `/plugin` недоступна):
  ставить скилл напрямую клонированием в папку личных скиллов. Репо — маркетплейс, сам скилл
  лежит в `skills/karpathy-guidelines/`:
  
  ```
  git clone --depth 1 https://github.com/forrestchang/andrej-karpathy-skills.git /tmp/karpathy
  mkdir -p ~/.claude/skills && cp -r /tmp/karpathy/skills/karpathy-guidelines ~/.claude/skills/ && rm -rf /tmp/karpathy
  ```
  
  Подхватывается сразу, рестарт обычно не нужен. Это один скилл — `karpathy-guidelines`.
- **Codex / Gemini / без плагинов** — применять 4 принципа из **раздела 3** текстом
  (раздел 3 и есть их содержимое).

## 11. Опциональный модуль: Superpowers

Набор скиллов-процессов: brainstorming (до любой реализации), test-driven-development,
systematic-debugging, verification-before-completion, executing/writing-plans и др. Управляют
тем, **как** подходить к задаче. Включать по ответу в чек-листе (дефолт: спросить).

- **Claude Code** — если набор уже установлен, вызывать скиллы инструментом `Skill` по
  ситуации (фича → brainstorming; код → TDD; баг → systematic-debugging; перед «готово» →
  verification). Если не установлен — поставить плагином (источник: `github.com/obra/superpowers`):
  
  ```
  /plugin marketplace add obra/superpowers-marketplace
  /plugin install superpowers@superpowers-marketplace
  ```
  
  Команды `/plugin` выполняет пользователь — подсказать их, не пытаться вызвать самому.
- **Codex / Gemini / без скиллов** — применять суть текстом: сначала брейншторм дизайна и
  согласование, тесты до кода, систематический дебаг (гипотеза → проверка), проверка
  реальным прогоном перед заявлением «готово».
- Приоритет при конфликте: правила пользователя > конституция проекта (если заведена, раздел 12)
  
  > Superpowers > дефолт агента.

## 12. Опциональный модуль: конституция проекта (по мотивам spec-kit)

По мотивам `github/spec-kit` (Spec-Driven Development). Берём из него ДВЕ идеи, БЕЗ установки его
CLI (`/speckit.*`, `.specify/` — дублирует наш `docs/superpowers` и слабее по ревью-гейтам).
Включать по ответу в чек-листе (дефолт: спросить). Проверено на F1 Predict (2026-07).

1. **Конституция** — файл `docs/constitution.md`: короткий свод НЕЗЫБЛЕМЫХ принципов проекта
   (безопасность, данные/время, инфраструктура, процесс с ревью-гейтами, код/зависимости, дизайн).
   Консолидирует уже принятые решения из плана/контекстных файлов в один якорь — ничего нового не
   выдумывать. На него сверяется каждая спека, план, реализация и ревью. Меняется осознанно:
   сначала правим конституцию, потом код.

   - **Прокидывать сабагентам:** холодный сабагент видит только свой промпт → вкладывать в промпт

2. **Coverage-check перед merge** (аналог `/speckit.analyze`) — явная проверка «код покрывает каждое
   требование спеки, нет дрейфа spec↔plan↔code» в финальном ревью ветки (Superpowers
   `finishing-a-development-branch`).

Приоритет: правила пользователя > конституция > Superpowers > дефолт агента.

## 13. Опциональный модуль: меньше permission-prompts

Встроенный скилл Claude Code `fewer-permission-prompts` (не требует установки). Сканирует
транскрипты последних сессий, считает частоту Bash/MCP-вызовов, отбирает read-only команды и
пишет allowlist в `.claude/settings.json` (командный файл, коммитится в git — не путать с
личным `.claude/settings.local.json`). Включать по ответу в чек-листе (дефолт: спросить).
Проверено на F1 Predict (2026-07).

- Полезнее не в самый первый момент (транскриптов ещё нет), а после того как накопилась хотя бы
  одна содержательная сессия работы — предложить прогнать скилл тогда же, а не только на старте.
- Скилл сам фильтрует: **никогда** не allowlist-ит интерпретаторы/шеллы с произвольным кодом
  (`node -e`, `python -c`, `bash -c` и т.п.), мутирующие команды (`git add/commit/push/merge`,
  `npm install`, `rm`, `mkdir`) и «скрытые интерпретаторы» — свои cloud-direct раннеры, которые
  берут SQL/код текстом и исполняют его (`node runner.js sql "<любой SQL>"` и подобные — даже если
  9 из 10 использований read-only, сам паттерн даёт выполнение произвольного текста).
- Вызывать: `Skill(fewer-permission-prompts)` — прочитает транскрипты и предложит приоритизированный
  список перед тем, как что-то менять.

Приоритет: правила пользователя > конституция > Superpowers > дефолт агента.

## 15. Опциональный модуль: оформление README

Два стиля README, спросить какой (или сделать оба на выбор — см. ниже). Включать по ответу
в чек-листе (дефолт: спросить). Проверено на F1 Predict (2026-07-24).

- **Традиционный** — коротко: назначение, быстрый старт, формула/API если есть, стек. Без
  бейджей и эмодзи-разделов. Подходит маленьким внутренним/разовым проектам, где README читает
  только сам автор или пара человек «в контексте».
- **Нарядный** (по мотивам `github.com/oil-oil/beautify-github-readme`) — hero-блок с бейджами
  (build/deploy статусы, стек), оглавление, ASCII-схемы (архитектура, жизненный цикл), таблицы
  вместо сплошного текста, подробные объяснения нетривиальных решений на уровне «джуна» (не
  просто «что», а «почему так»). Подходит проектам, которые показывают другим (портфолио,
  открытый или полуоткрытый репозиторий, ждём внешних читателей/контрибьюторов), и там, где
  сам README должен объяснять нетривиальные архитектурные решения, а не только команды запуска.
- Если пользователь не уверен — сделать оба (`README.md` традиционный + `README_new.md`
  нарядный) и дать сравнить визуально, прежде чем выбрать один как основной. Так и решили на
  F1 Predict: нарядный вариант писать по фактам из кода/миграций/конфигов проекта, не
  выдумывать факты и не тащить неподтверждённые формулировки из старых доков (CLAUDE.md/план
  могли устареть — сверяться с реальным кодом).
- Собирая нарядный вариант, для каждого нетривиального решения (например, "почему нет своего
  бэкенда", "почему секреты не в коде") явно объяснять причину, а не просто констатировать факт —
  это и есть разница между «для джуна» и обычным README.

Приоритет: правила пользователя > конституция > Superpowers > дефолт агента.

## 16. Опциональный модуль: карта архитектуры для агента (HTML + JSON)

Два файла в корне проекта — `architecture-map.html` (для человека) и `architecture-map.json`
(для следующего сабагента). Включать по ответу в чек-листе (дефолт: спросить — полезно, когда
проект дорос до нескольких подсистем и/или используется subagent-driven-development; для
маленького проекта избыточно). Проверено на F1 Predict (2026-07-26).

- **`architecture-map.html`** — самодостаточная (без внешних CDN/шрифтов — офлайн-надёжность)
  визуальная карта: стек, структура репозитория, схема БД (таблицы/связи/RLS/функции), схема
  автоматики (workflows + расписание), roadmap, формула/бизнес-логика если есть, и отдельный
  раздел **«гварды/гочи»** — неочевидные инварианты, которые агент иначе узнаёт только через
  чтение кода или ошибку (например «X нигде не используется, хотя старые доки утверждают
  обратное», «команда Y необратимо сносит прод — не гонять не думая»).
- **`architecture-map.json`** — та же информация машиночитаемо, тем же набором разделов
  (project/stack/structure/database/automation/scripts/frontend/gotchas/secrets/docs), плюс
  `meta.staleness_policy` — явное указание, что файл не автообновляется и как его актуализировать.
  Вкладывать в промпт свежему сабагенту (subagent-driven-development) вместо ручной сборки
  контекста по задаче — экономит подготовительную работу контроллера.
- **Расположение — корень проекта, не `docs/`.** На F1 Predict изначально положили в `docs/`
  вместе с спеками/планами, пользователь указал, что это неочевидное место — переехали в корень
  рядом с `README.md`/`ARCHITECTURE.md`/`MEMORY.md`, где и так лежат главные context-файлы.
- **Не обновлять автоматически на каждом `git save`** (см. раздел 6, пункт про `git save`) —
  спрашивать пользователя только тогда, когда меняется структура/схема/автоматика (то же
  событие, что требует правки `ARCHITECTURE.md`), не на каждый коммит. Цель — не жечь токены
  впустую на пересборку карты, когда архитектура не изменилась.
- Оба файла — снимок на момент создания, не живой источник правды; при расхождении с кодом
  доверять коду, карту — поправить.

Приоритет: правила пользователя > конституция > Superpowers > дефолт агента.
